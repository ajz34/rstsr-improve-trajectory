## 0. Reconnaissance done for this round (facts, not opinion)

**Is indexing still the blocker?** No — basic indexing landed in `d7f4082`
(int/slice/newaxis/ellipsis/`()` keys, `__setitem__` for basic keys). The
suite's per-element verification helpers (`out[idx]`, `iter_indices`,
`ndindex`) now work; test_array_object is 19/27. What remains blocked on
rust-side indexing is only the mask/fancy family (G-035/038/039).

The real W2 blockers found by reading the suite (`6c0b59f`) and the shim:

1. **Verification paths.** `test_special_cases` (`test_unary`/`test_binary`/
   `test_iop`, 482 current failures) and `test_operators...`
   (`*_assert_against_refimpl`, per-index loops) verify with `float(out)` /
   `res[idx]` only — **no `xp.where`, no fancy helpers**. So the large
   elementwise block is genuinely unblocked by W1.
   `xp.where` (G-037) is only needed by `ph.assert_array_elements`, used by
   test_array_object (already blocked), test_positive, and a few
   creation/manipulation tests — a W2 tail item, not a gate.
2. **Mixed dtypes (G-009).** Every binary elementwise param draws its
   operand dtypes from the suite's promotion table
   (`oneway_promotable_dtypes`), i.e. equal or one-way-promotable pairs.
   rstsr's kernels split:
   - promotion-capable **today** (kernel bound on `DTypePromoteAPI`):
     `maximum minimum floor_divide atan2 copysign hypot nextafter logaddexp`
     + the 6 comparisons;
   - same-type only (bound on Rust `Add`/`Sub`/`Mul`/`Div`/`Rem`/bitops/
     `Pow`): `add subtract multiply divide remainder bitwise_* shl shr pow`.
   → mixed pairs of the first family are servable by a *shim-side* pair
   dispatch; the second family needs a rust-side change.
3. **Dtype-output rules.** Extracted from the 2025.12 spec stubs
   (`array-api/src/array_api_stubs/_2025_12/elementwise_functions.py`):
   - "same dtype as input": `ceil floor trunc round sign conj positive
     bitwise_invert nextafter(same as x1)`; `abs` (real→same, complex→real).
   - "floating-point, per promotion": the transcendental family; **inputs
     should be floating-point** (so ints are out of contract — the suite
     only draws floats for them).
   - "determined by type-promotion": `add subtract multiply divide square
     pow remainder floor_divide maximum minimum bitwise_*`.
   - `ceil/floor/trunc` take **real-valued** inputs (integers included) and
     must return **the same dtype as the input**; `round` takes
     numeric (incl. complex); `logical_*` are bool-only.
   - Consequences vs rstsr: `rt::{ceil,floor,trunc,round}_f` bound on
     `Float` and promote integers to f64 (`TOut = T::FloatType`) → wrong
     result dtype for integer inputs; `round` has no complex kernel
     (`DTypeIntoFloatAPI` + `Float` bound); `sign`/`square`/`abs` are
     dtype-correct already.
4. **Scalar operands** (`x op s`): the shim's `_operand` cast-to-array-dtype
   policy matches the spec for same-kind scalars, and the `(x, s)` params
   already pass. Cross-kind scalars (e.g. float scalar + int array) are
   refused; that is the same G-009 family (needs promotion).

## 1. R4-Q1 — mixed-dtype binary operands: how far does the shim go in W2?

Options:
- **(a) Pair dispatch in the shim's Rust for the promotion-capable family**
  (maximum/minimum/floor_divide/atan2/copysign/hypot/nextafter/logaddexp +
  comparisons); `add/sub/mul/div/rem/bitwise_*/shl/shr/pow` stay
  same-dtype + register. Uses rstsr's own `DTypePromoteAPI` (no duplicated
  promotion table), at the cost of a 13×13 expansion per op (generated by a
  nested macro; compile time to be measured).
- (b) Same-dtype only everywhere; every mixed-pair test stays red and
  registered.
- (c) Stop and request rust-side promotion wiring for the whole binary
  family first (blocks the W2 binary half on the maintainer).

**Recommendation: (a).** It is shim-side binding work (no algorithm, no
promotion table of our own), maximizes this pass, and leaves a clean
rust-side request for the arithmetic family.

## 2. R4-Q2 — integer inputs to `ceil/floor/trunc/round` (and cousins)

The spec demands dtype preservation for these; rstsr promotes ints to f64
(and has no complex `round`).

- **(a) Shim casts the result back to the input dtype for integer inputs**
  (value-exact for these functions), with a register entry, in the spirit
  of the existing G-018 cast table; complex `round` registered rust-side.
- (b) Rust-side: make the rounding family dtype-preserving for integer
  inputs (and decide complex round support) — waits on the maintainer,
  W2's rounding tests stay red meanwhile.
- (c) Decline integer inputs (tests stay red, honest but no progress).

**Recommendation: (a) + register (b) as the rust-side item.**

## 4. R4-Q4 — `positive` / `__pos__` and other absent-primitive tails

`positive` has no rt primitive. The wrappers could `return self` (or a
copy), which is value-correct but defines aliasing semantics and is a
"fallback for a missing op" under the wrapper rule. The rest of the W2
neighborhood (`where`, `sort/argsort`, `roll/repeat/tile`, `clip`,
`cumulative_*`, `nonzero`, `unique_*`, `searchsorted`, `isin`,
`take_along_axis`, linalg gaps) is registered rust-side and out of scope.

- (a) Register `positive`/`__pos__` rust-side; skip in W2 (recommended).
- (b) Allow the shim to return `self` / a copy for `positive` (needs your
  explicit per-case permission under the wrapper rule).
