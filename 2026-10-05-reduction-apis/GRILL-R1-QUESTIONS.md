## Background (agent-verified facts, 2026-10-05)

Current state (rstsr `main` @ 71ac4d2, clean):

- Reduction traits `Op{Sum,Min,Max,Prod,Mean,Var,Std,L2Norm,ArgMin,ArgMax,NanArgMin,NanArgMax,All,Any,CountNonZero}API<T, D>` with assoc `type TOut` (`rstsr-core/src/operators/reduction.rs`), generated by `#[duplicate_item]`. Tensor level: `<fam>`, `<fam>_all` (scalar), `<fam>_axes` (+ `_f` twins) via `trait_reduction!` (`src/tensor/reduction.rs`).
- `TOut = T` for sum/min/max/prod/mean; `T::Real` for var/std/l2_norm; `usize` for arg*/count_nonzero; `bool` for all/any; bool-sum → `usize`. mean/var/std reject integers at compile time (`ComplexFloat + FromPrimitive`); `sin`-family accepts ints via `DTypeIntoFloatAPI::FloatType` (int → f64).
- keepdims: nowhere. `out=`: nowhere. No tensor-level `astype` (cross-dtype kernel exists: `OpAssignAPI` + `DTypeCastAPI`). No rt-level user-closure reduce, but `rstsr-native-impl` has closure-generic `reduce_all/reduce_axes_cpu_serial[_rayon]` (init / f / f_sum / f_out).
- faer-py (#108 merged): `test_statistical_functions` 0/9 — mean/prod/std/var/max/min unbound; cumulative_sum/prod missing everywhere (C5); `sum`: `axis=` unbound, `dtype=` kwarg rejected, uint8-sum returns uint8 (G-043). Wrapper-only directive: shim carries no algorithms.
- Spec (array-api 2025.12): sum/prod `(x, *, axis, dtype, keepdims)`; mean `(x, *, axis, keepdims)` — **no dtype param**; cumulative_sum/prod `(x, *, axis, dtype, include_initial)` — no keepdims/reverse; dtype=None widens small ints (signed → default int, unsigned → same-bits unsigned) and explicit dtype "should" cast input **before** computing (anti-overflow); vector_norm `(x, *, axis, keepdims, ord=2)` — ord numeric only, incl. non-norms 0/-inf/p<1, axis=None flattens to 0-D; matrix_norm `ord ∈ {'fro','nuc',1,-1,2,-2,inf,-inf}` (2/-2/nuc need SVD); no user-callable reduce anywhere in the spec.
- NumPy: `np.sum/cumsum/cumprod(axis=None, dtype=None, keepdims)` (flatten-on-None; extra `initial/where/out`); `np.linalg.norm(x, ord=None, axis=None, keepdims=False)` ord table shared with scipy; scipy `norm` falls back to np + BLAS fast paths.

## Questions

❓ **Q1** - **Normative contract**: array-api 2025.12 or NumPy where they differ?
Differences that matter: (a) `cumsum(axis=None)` flattens in NumPy but is an error
for ndim>1 per spec; (b) NumPy has `initial/where/out` extras; (c) norm `ord`
strings ('fro'/'nuc') exist in NumPy/SciPy, numeric-only for array-api
vector_norm; (d) NumPy `cumsum` widening rule for unsigned may differ from the
spec's (np says "default platform integer"; spec says same-bits unsigned).

➡️ Recommend: array-api 2025.12 is the normative contract (it is what
array-api-tests grades, and the 2026-10-02 directive says compliance beats
efficiency); NumPy is the test oracle and cross-check via the existing
numpy-transcription test style; rstsr may keep NumPy-style supersets (e.g.
flatten-on-None) only where they cannot fail the suite, documented under
"Notes of API accordance".

❓ **Q2** - **Default output dtypes — accept the breaking changes?**
To satisfy the dtype=None rules: sum/prod/cumulative_* of i8/16/32 → i64 and
u8/16/32 → u64 (floats/complex unchanged); mean/var/std accept integer input and
return default float (f64) via the `sin`-pattern (`DTypeIntoFloatAPI`); min/max
stay TOut=T. bool-sum stays `usize` (spec wants default int i64 on the Python
side — propose handling that at the shim binding, not by changing Rust `usize`).
This changes existing signatures (`sum(i32)` → `Tensor<i64>`), user code, and
numpy-transcribed tests.

➡️ Recommend: yes — spec-mandated (G-043) and NumPy-faithful; implement the
widening as a new type-level trait in rstsr-dtype-traits (name TBD, e.g.
`DTypeWidenAPI`/accumulator-default) so `TOut` becomes a computed assoc type;
breaking note in CHANGELOG.

❓ **Q3** - **Explicit output dtype — which mechanism?**
Options: (A) cast-composition at the tensor layer: add a public tensor-level
cast (astype-like, built on `DTypeCastAPI`/`OpAssign`) — `sum` with dtype =
cast-then-reduce; the *default* widening of Q2 is the same composition with the
widen trait, so device traits keep `TOut = T` and the fold happens in the wide
type (spec-faithful anti-overflow). Costs one intermediate cast allocation;
efficiency explicitly not the concern. (B) Parameterize `OpReduceAPI` over TOut
(invasive: every device impl). (C) `_from`/with-output-tensor pattern (caller
passes output). User-facing spelling under (A): compose
`x.to_cast::<f64>().sum_with_args(...)` vs a generated convenience
`sum_dtype::<f64>(x, axes, args)` (turbofish, since a dtype has no runtime value
to infer from — same reason `IsCloseArgs<TE>` carries floats).

➡️ Recommend: (A) + generated thin `*_dtype::<TOut>` convenience wrappers;
no device-trait refactor; the new public tensor cast API also fills a real gap
(faer-py needs `astype` for W5 anyway).

❓ **Q4** - **`*_with_args` surface and keepdims coverage**:
Proposed: `ReduceArgs { keepdims: Option<bool> }` (ReshapeArgs style: all-Option
fields, `Default`, `From`-overloads, `impl Into<ReduceArgs>`); macro generates
`<fam>_with_args[_f](x, axes, args)` + TensorAny methods for **all** reduction
families uniformly (incl. arg*/all/any/count_nonzero — spec has keepdims on
them; fixes G-041); existing `<fam>`, `<fam>_axes`, `<fam>_all` stay as thin
wrappers; axes stay a positional parameter (like reshape's shape); whole-reduce
with keepdims → shape `(1,) * ndim`. var/std additionally get
`VarArgs { keepdims, correction }` (array-api `correction`, `M - correction <= 0`
→ NaN) instead of plain ReduceArgs.

➡️ Recommend: adopt as proposed; one shared ReduceArgs, VarArgs for var/std;
no per-family args structs beyond that (cumulative gets its own, see Q6).

❓ **Q5** - **`norm` family — scope and ord representation**:
Proposed surface per your prompt: `norm(x, ord)`, `norm_axes(x, ord, axes)`,
`norm_with_args(x, ord, axes, args)`. Ord as an enum (`NormOrd`) rather than
strings/floats: variants for 1, 2, Inf, -Inf, 0, -1, -2, P(f64) (arbitrary Lp,
covers p<1 non-norms), Fro, Nuc — `From<f64>` maps 1.0→One, 2.0→Two, ±inf→Inf,
else P. Semantics: scipy/NumPy-style (axis=None flattens; int input cast to
float first; TOut = `T::Real`; complex → real). Scope question: vector norms +
Frobenius are pure composition (abs/pow/sum/argmin-max over column/row sums);
matrix 1/-1/inf/-inf likewise composed; **2/-2/nuc need SVD** — include now
(faer SVD exists) or defer to the linalg wave (W6)?

➡️ Recommend: enum + From overloads as above; this round implements vector
ords + Fro + matrix 1/-1/inf/-inf via composition; defer SVD-dependent
matrix 2/-2/nuc to W6 (register as gap); keep `OpL2NormAPI`/`l2_norm` as the
fast path, `norm(Two)` may route to it later.

❓ **Q6** - **`cumulative_sum`/`cumulative_prod` semantics**:
Names per spec (`cumulative_sum`, not `cumsum`). Single axis only (NumPy/spec
both). `axis=None`: flatten (NumPy superset, cannot fail the suite) or
spec-strict (error for ndim>1)? `CumSumArgs { include_initial }` (+dtype via Q3
mechanism); no `reverse` (neither NumPy nor spec has it). Unsigned widening:
follow the spec rule (same-bits unsigned) even if NumPy cumsum maps to platform
int — pin exact behavior when transcribing NumPy tests. New device trait +
serial and rayon kernels (parallel scan optional; serial first).

➡️ Recommend: flatten-on-None (document as NumPy-parity superset),
`CumSumArgs { include_initial: bool }`, spec widening rule, serial kernels
first.

❓ **Q7** - **User-supplied reduction — API shape**:
Surface the native-impl closure machinery at rt level:
`reduce_all[_f]` / `reduce_axes[_f](x, axes, args, init, fold, combine, finalize)`
with accumulator TS and output TO generic; `fold: Fn(TS, &T) -> TS` (element),
`combine: Fn(TS, TS) -> TS` (partials — needed for rayon; must be associative),
`finalize: Fn(TS) -> TO`; closures `Send + Sync` (rayon requirement — known
gotcha); new device trait generic over the closures, implemented for
DeviceCpuSerial + DeviceFaer; keepdims via the same ReduceArgs. Lp-norm as the
doc example (your motivating case).

➡️ Recommend: adopt exactly this shape (4 params + init); free functions only
(no TensorAny methods — rare, expert-level API); document associativity
requirement on `combine`.
