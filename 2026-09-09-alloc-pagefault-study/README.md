# T7 — alloc-pagefault study (no patch)

Campaign task T7: **quantify the allocation/page-fault "fault rider"** in
rstsr's allocating ops at base commit
`386948be819baa334b8da02232f3a1944e5447d5`, and evaluate remedies at four
levels: glibc env tunables, existing rstsr APIs, allocator/pool design, and
transparent huge pages.

- **MEASUREMENT-ONLY task.** No code changes to the rstsr tree — verified
  `git -C ../../rstsr status --short` empty and HEAD `386948b` at start and

## What was measured

For each op × size × device, two policies:

- **A_alloc** — idiomatic allocating call (output storage allocated inside
  the op every iteration; T0's policy).
- **B (reuse)** — output storage allocated ONCE outside the timed loop:
  - `B_reuse_mutc` — **single pass** into the existing buffer via the public
    rstsr-core fn `op_mutc_refa_refb_func(c, a, b, f)` (found in
    `rstsr-core/src/tensor/operators/op_with_func.rs`; add contig/strided).
  - `B_reuse_2pass` — existing tensor methods `c.assign(&a); c += &b;`
    (`rstsr-core/src/tensor/assignment.rs`, `op_binary_assign.rs`).
  - `B_reuse_assign` — `c.assign(&a.t())` for transpose copy.
  - `B_reuse_fill` — `c.fill(v)` for full/zeros.
  - `B_bound` — **emulated kernel bound, not an rstsr API**: raw single-pass
    loop into a preallocated `Vec` (serial = 1 thread; the faer id runs 16
    std threads, `B_bound_par16`).

Correctness gate (`examples/correctness.rs`): every reuse/emulated variant is
checked against the allocating call AND a naive scalar reference — odd size
1000×777, explicit zero-stride broadcast view, both devices, both RUSTFLAGS
configs (`results/correctness_{portable,native}.txt`, all pass).

## The rstsr allocation path (why the faults happen)

`Tensor` storage on CPU goes: device `uninit_impl`
(`rstsr-core/src/device_cpu_serial/creation.rs`,
`feature_rayon/auto_impl/creation.rs` for faer) →
`uninitialized_vec` (`rstsr-common/src/alloc_vec.rs`) → with the
`aligned_alloc` feature and len > 128 elements:
`aligned_uninitialized_vec::<T,128>(size, 64)` → `aligned_alloc(bytes, 64)`
→ `std::alloc::alloc(Layout::from_size_align(bytes, 64))` → glibc.

For a fresh 32 MiB output (2048×2048 f64) glibc serves the chunk by `mmap`
and `munmap`s it on free (see mechanism below), so every byte of the output
is a zero-page mapped on first touch: **8193 minor faults per iteration
(32 MiB / 4 KiB + 1), identical for every allocating op**. Reuse variants
show ~0 faults/iter after warm-up (page-table + allocator noise only).

**Mechanism (why glibc doesn't adapt):** glibc raises its dynamic mmap
threshold when freeing an mmap'd chunk *up to `DEFAULT_MMAP_THRESHOLD_MAX`
= 32 MiB (LP64)*. A 2048×2048 f64 output (33 554 432 B + chunk header +
64-B alignment padding) has chunksize **just above the cap**, so the
threshold is never raised and every alloc/free pair is an mmap/munmap. At
medium (512×512 = 2 MiB) and odd (1000×777 = 6.2 MiB) sizes the chunk is
under the cap, the threshold adapts, and **the rider is already ~0 without
any tuning** — measured below. This explains why T0 saw the rider only in
the large class.

# RQ1 — How big is the fault rider?

Criterion, native config (portable in `results/tables.md`, same picture).
**Statistics: the headline tables quote criterion's *mean* point estimate
from `new/estimates.json` (regenerated by `results/make_tables.py`);
criterion's *median* differs by ≲0.5% on these runs and changes no
conclusion.**
Rider = (A − best B) / A, i.e. the wall-time share removable by never
allocating the output inside the op.

| group | case (2048×2048 f64 unless noted) | A_alloc | best reuse (API) | emulated bound | rider |
|---|---|---|---|---|---|
| add contig | serial | 6.318 ms | 2.154 ms (`op_mutc`) | 2.173 ms | **66%** |
| add contig | faer16 | 2.741 ms | 0.629 ms (`op_mutc`) | 0.719 ms (16×std) | **77%** |
| add strided (`a + bt.t()`) | serial | 28.298 ms | 23.041 ms (`op_mutc`) | 17.249 ms | 39% (bound incl. kernel win) |
| add strided (`a + bt.t()`) | faer16 | 4.144 ms | 2.122 ms (`op_mutc`) | 1.306 ms (16×std) | 68% (bound incl. kernel win) |
| transpose copy | serial | 22.809 ms | 17.309 ms (`assign`) | 17.061 ms | **25%** (pure fault part) |
| transpose copy | faer16 | 3.544 ms | 1.507 ms (`assign`) | 1.512 ms | **57%** |
| transpose copy | odd 1000×777 serial | 2.430 ms | 2.443 ms (`assign`) | 0.330 ms | 0% rider; 86% is **kernel** (T1's target) |

|---|---|---|---|

| add `op_mutc` serial | 2.16 | 0.0 | 0% |

| add `op_mutc` faer16 | 0.64 | 0.2 | 3% |

| full `fill` serial | 0.57 | 0.1 | 15% |

T0's 844k-fault/100-iter add_contig profile reproduces exactly
(`results/perf/perf_add_a_serial.txt`: 843 968 page-faults).

**Answer RQ1:** the rider is a **large-class phenomenon**: ~4 ms fixed cost
per fresh 32 MiB output (≈ 8193 zero-page faults, sys-time-bound), i.e.
**66% of add, 25% of transpose copy, 88% of `full`** in wall time at
2048×2048; 57–77% on the faer path for add/transpose. At medium/odd sizes
it is already ~0 (glibc's dynamic threshold adapts). Small outputs
(sum_axis0, batched vecdot) never had a rider — the negative controls show
**zero** fault overhead, so kernel-work gaps there (e.g. sum_axis0's 3× vs
the naive bound) belong to T1/T2 kernel tasks, not to allocation.

# RQ2 — Remedy level

## (a) glibc env tunables — recovers ~96% with NO code change

`add_a` 2048² (native; `results/tunables/`):

| env | serial ms/iter | faults/iter | faer16 ms/iter | faults/iter |
|---|---|---|---|---|
| default | 6.18 | 8193 | 2.70 | 8224 |
| `MALLOC_MMAP_THRESHOLD_=33554432` (32 MiB) | 6.36 | 8193 | 2.90 | 8226 |
| `MALLOC_MMAP_THRESHOLD_=67108864` (64 MiB) | 4.42 | 4407 | 2.64 | 7081 |
| **`MALLOC_MMAP_THRESHOLD_=67108864` + `MALLOC_TRIM_THRESHOLD_=134217728`** | **2.27** | **82** | **0.72** | **41** |
| `MALLOC_TRIM_THRESHOLD_=134217728` alone | 6.35 | 8193 | 2.98 | 8225 |
| `MALLOC_TOP_PAD_=33554432` | 6.06 | 7947 | 2.85 | 8225 |
| `MALLOC_ARENA_MAX=1` | 6.11 | 8193 | 2.93 | 8225 |

- The 32 MiB threshold value is a trap: the chunk (size + header + padding)
  is *larger* than the threshold, so it still mmaps. The threshold must
  **exceed** the largest recurring allocation (64 MiB here).
- Raising mmap threshold alone halves the cost; the trim threshold must
  follow or `free()` shrinks the brk heap and refaults happen anyway.
- **Recovery: (6.18−2.27)/(6.18−2.16) = 97% serial, (2.70−0.72)/(2.70−0.64)
  = 96% faer16**, against the reuse variants. The env-tuned *allocating* op
  (2.27 ms) essentially ties the reuse API (2.16 ms).
- Cost/risk: resident memory grows (freed buffers stay mapped; peak RSS ≈
  working set × transient outputs); not a per-process default for a
  library — it is a **user-side, per-job env setting** and belongs in docs.

## (b) existing rstsr API — a single-pass reuse path already exists

Found at 386948be and measured above:

1. `op_mutc_refa_refb_func(c, a, b, &mut |c, a, b| c.write(a + b))`
   (`rstsr-core/src/tensor/operators/op_with_func.rs`, public via
   `rstsr_core::tensor::operators::exports`). Writes `c <- a ⊕ b`
   elementwise into existing storage in **one pass**, with broadcasting and
   arbitrary layouts, for both devices (faer path is parallel). It is the
   same driver `mapb_*` uses after allocating; used directly it skips the
   allocation entirely. Measured: add 2048² serial 2.15 ms (vs 6.32
   allocating), faer16 0.63 ms (vs 2.74). *Caveats: low-level signature
   (`MaybeUninit` closure, `impl TensorViewMutAPI`), not exposed through
   `rt::`, undocumented as a reuse idiom, and there is no tensor-method
   sugar like `c.addfrom(&a, &b)`.*
2. `c.assign(&src)` — tensor-method assignment into existing storage
   (supports strided/broadcast sources): transpose-copy reuse (17.3 ms vs
   22.8 ms serial; 1.51 vs 3.54 faer16).
3. `c += &b` (`add_assign`) + `c.assign(&a)` — a two-kernel-pass composition
   (2.52 ms serial large add) — works but pays an extra R+W pass over
   `op_mutc`.
4. `c.fill(v)` — in-place fill (0.54 ms vs 4.48 ms for `rt::full`).
5. `rt::zeros` is calloc-lazy — already optimal; do not touch (T0's
   conclusion, reconfirmed: 2.4 µs, 1 fault/iter).

**Answer RQ2b: yes — for every op in the matrix except reductions there is a
working reuse path today, and it recovers the full measured rider.** What's
missing is discoverability/ergonomics, not mechanism.

## (c) allocator/pool design (edit-guide sketch only, not built)

A device-level buffer pool (size-class free-lists in
`DeviceCpuSerial`/`DeviceFaer` storage allocation) would make *idiomatic*
allocating code fast with zero user changes: after warm-up, `alloc` returns
the just-freed buffer (no mmap, no faults — the `reuse` mode of the THP
probe shows the floor: 0.36–0.50 ms/iter for a 32 MiB fill). Trade-offs:
pool memory high-water marks, thread-local vs global lists (faer's pool has
16 allocating threads), interaction with `aligned_alloc`'s 64-B layout, and
release semantics. This is a real but invasive option; the evidence says its
ceiling equals what env tunables + reuse APIs already deliver.

## (d) huge pages — madvise(MADV_HUGEPAGE) hides the fault cost, but not on rstsr's current buffers

System THP state: `enabled = [madvise]`, `defrag = [madvise]` — user buffers
stay 4 KiB unless explicitly hinted.

Probe (`examples/madvise_thp.rs`, 32 MiB fresh alloc + fill, 200 iters):

| mode | ms/iter | minor faults/iter |
|---|---|---|
| plain: 64-B-aligned alloc (rstsr's path) | 4.20 | 8193 |
| **2-MiB-aligned alloc + `MADV_HUGEPAGE` + fill** | **0.68** | **18** |
| persistent buffer (floor) | 0.50 | 0 |
| persistent + re-hint | 0.54 | 0 |

- With huge pages the fresh-allocation cost nearly reaches the reuse floor
  (16 huge faults instead of 8192).
- **Blocker (expected per POSIX, observed during development):** calling
  `madvise` on rstsr's actual buffers is expected to fail — `madvise`
  requires a page-aligned address, and glibc's memalign trim path returns
  64-B-*aligned*, not page-aligned, pointers for rstsr's 64-B alignment
  (`EINVAL`, observed during development; no raw log committed). A THP
  integration in rstsr would have to change the allocation alignment (4 KiB
  minimum, 2 MiB for THP), not just add a hint call. Alignment 2 MiB showed
  no measurable allocation slowdown.

# RQ3 — Ranking: which ops/sizes benefit most

By wall-time share recoverable (large 2048×2048 class, both devices):

1. **`full`/`ones`/`linspace`-class creation ops — 88%** (allocation IS most
   of the op: 4.48 → 0.54 ms).
2. **elementwise add contig — 66% serial / 77% faer16** (6.32 → 2.15 ms).
3. **add strided — 68% faer16** (4.14 → 2.12 ms `op_mutc`); serial 39% rider
   plus a 17.2 ms kernel-bound floor → the fault fix alone (23.0 ms) is
   modest there; T4's kernel work is the bigger serial lever.
4. **transpose copy — 57% faer16 / 25% serial** (3.54 → 1.51 ms faer16).
5. **small outputs (sum_axis0, batched vecdot) — ~0%**: no rider; judge
   kernel work against kernel-only denominators (T1/T2/T3 unaffected by
   this study).
6. **medium/odd sizes — 0–5%**: glibc already adapts; only >~32 MiB fresh
   outputs pay.

**Denominator guidance for later tasks (T1–T5):** under criterion's
alloc-included policy, a kernel improvement to a large-class allocating op
can be masked or exaggerated by the ~4 ms rider. Kernel wins must be judged
kernel-only (reuse variant / bound) when the op allocates a ≥32 MiB output;
e.g. T1's transpose kernel (2.43 ms odd, bound 0.33 ms) is invisible in the
fault noise of a fresh 6 MiB–32 MiB output... and indeed `B_reuse_assign`
(2.44 ms) shows zero of the odd-size transpose win unless output reuse is
assumed.

# RQ4 — Does the rider interact with the rayon path differently?

No, in relative terms. faer16 variant A shows the **same absolute fault
count** (8225 vs 8193/iter — the output is mmap'd once by the calling
thread, faults distributed over first-touching workers), and a similar wall
share: add A faer16 2.51 ms vs 0.64 ms reuse → **75% rider** (serial 67%).
perf: faer16 add A sys/user = 3.42/2.01 s over 200 iters — fault handling
aggregates across the pool but still dominates. Sixteen concurrent fault
streams do not make it per-byte worse (kernel side serializes on the mmap
locks anyway), and `MALLOC_ARENA_MAX=1` alone changed nothing (large
allocations bypass arenas). The remedy levels also transfer unchanged:
env-tunable recovery 96% faer16, reuse API 77%+ recovery faer16.

# Honest-negative clause

**The fault rider is NOT universal — it is a >32 MiB-fresh-output
phenomenon on glibc.** For medium (2 MiB) and odd (6.2 MiB) sizes the
measured rider is 0–5% (glibc's dynamic mmap-threshold adaptation handles
them); for small outputs (reductions, vecdot) it is exactly 0. Ops with
small outputs have real gaps (sum_axis0 3×, transpose-odd 7× vs naive
bounds) but those are **kernel** gaps for T1/T2, not allocation gaps. If
typical workloads allocate outputs < 32 MiB, the right guidance is "no
action"; the guidance below applies to streaming-size outputs (≥ ~32 MiB
fresh allocations per op), which is exactly the large class of the campaign
matrix and a common HPC case (grid arrays, wavefunctions, integral
containers). (One noisy cell in the secondary portable table —
`add_contig odd_1000x777-serial` shows A and `B_reuse_mutc` elevated by the
same amount with a 22% gap to the raw-loop bound — is run/codegen noise
under the no-AVX build, not a fault effect: getrusage shows ~0 faults/iter
at this size. See `results/tables.md`.)

# Deviations from the brief

- Variant B for add: the brief anticipated `c.assign(&expr)`; the actual
  best existing API is the lower-level public `op_mutc_refa_refb_func`
  (single pass). `c.assign(&a); c += &b` (2-pass) is measured as a separate
  variant; both are reported.
- `MALLOC_MMAP_THRESHOLD_=33554432` (the brief's suggested value) turned out
  to be below the effective chunk size and does nothing; 67108864 (+
  trim threshold) is the working setting. Both are reported.
- faer16 `B_bound` uses 16 std::thread spawns per iteration (no rayon dep in
  this crate); spawn overhead (~10 µs) is visible at small sizes and makes
  the bound conservative. The faer reuse comparisons rest on `op_mutc` /
  `assign`, which run on the device's own rayon pool.
- The THP probe needed 2 MiB alignment for the madvise modes (rstsr's 64-B
  alignment yields non-page-aligned buffers → `EINVAL`, expected per POSIX
  since madvise requires a page-aligned addr, observed during development);
  the plain mode keeps rstsr's exact 64-B path. See RQ2d.
- `libc` added as a study-only dependency (getrusage, madvise).
- First portable criterion run's text log was lost to a missing directory
  (raw estimates were saved); the log was regenerated by re-running the
  suite. All raw criterion JSONs are committed under `results/*/criterion/`.
