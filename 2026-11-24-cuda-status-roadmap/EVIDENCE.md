## 2. Trait inventory (how the missing lists were derived)

Rustdoc HTML for the two device structs was generated by a prior local build
under `target/doc/`. Regenerate with:

```bash
cargo doc -p rstsr-cuda --no-deps
cargo doc -p rstsr-core --no-deps
```

Then extract every `id="impl-…"` entry, URL-decode it, keep the impls whose
`for-` type is the device struct, and compare **trait names** (not the full
generic header — the generic arity differs between CPU and CUDA for traits that
are implemented on both):

```python
import re, html, urllib.parse
def traits(path):
    s = open(path, encoding='utf-8').read()
    out = set()
    for m in re.finditer(r'id="(impl-[^"]+)"', s):
        i = html.unescape(m.group(1))
        if '-for-' not in i:
            continue
        head = urllib.parse.unquote(i.split('-for-')[0][5:])
        out.add(head.split('<')[0])
    return out
c = traits('target/doc/rstsr_cuda/device/struct.DeviceCuda.html')
p = traits('target/doc/rstsr_core/device_cpu_serial/device/struct.DeviceCpuSerial.html')
print(sorted(p - c))
```

Counts: 214 trait names on `DeviceCpuSerial`, 168 on `DeviceCuda`.

After dropping blanket/sugar traits that are not gaps
(`ByRef`, `Imply`, `Pointable`, `DeviceNumAPI`, `DeviceComplexFloatAPI`,
`Display`, `ToString`), the CPU-only set is:

**Device traits (11):**
`DeviceArrayIndexAPI`, `DeviceArrayIndexAssignAPI`, `DeviceCreationTriAPI`,
`DeviceExtCrossAPI`, `DeviceExtMatMulAPI`, `DeviceExtOuterAPI`,
`DeviceExtTensordotAPI`, `DeviceExtVecdotAPI`, `DeviceMaskIndexAPI`,
`DevicePutAlongAxisAPI`, `DeviceTakeAlongAxisAPI`.

**Op traits (26):**
`OpAllCloseAPI`, `OpArgSortAPI`, `OpCumProdDtypeAPI`, `OpCumSumDtypeAPI`,
`OpExtBitAndAPI`, `OpExtBitOrAPI`, `OpExtBitXorAPI`, `OpExtShlAPI`,
`OpExtShrAPI`, `OpIsCloseAPI`, `OpIsinAPI`, `OpLConsumeRemAPI`, `OpNegAPI`,
`OpNonzeroAPI`, `OpPackTriAPI`, `OpRConsumeRemAPI`, `OpRConsumeShlAPI`,
`OpRConsumeShrAPI`, `OpReduceCustomAPI`, `OpSearchSortedAPI`, `OpSortAPI`,
`OpSortCustomAPI`, `OpUniqueAPI`, `OpUnpackTriAPI`, `OpUnraveledArgMaxAPI`,
`OpUnraveledArgMinAPI`.

**Host-closure traits (9):**
`Op_MutA_API`, `Op_MutA_NumB_API`, `Op_MutA_RefB_API`,
`Op_MutC_NumA_RefB_API`, `Op_MutC_RefA_NumB_API`, `Op_MutC_RefA_RefB_API`,
`Op_MutD_RefA_RefB_RefC_API`, plus `OpReduceCustomAPI` and `OpSortCustomAPI`
(the last two are already counted in the 26 above). These are by-design
impossible on an accelerator, not pending work; 24 of the 26 op traits are
implementable.

**Linalg (19):** `rstsr-linalg-traits` entries, all implemented for
`DeviceFaer`, 12 also for the selected `DeviceBLAS` via
`rstsr-linalg-traits/src/blas_impl/*`. That module is written against the
compile-time `DeviceBLAS` alias (`use crate::DeviceBLAS;`), so it does not
apply to `DeviceCuda`. Full list in
[STATUS.md](STATUS.md) §5.

**Why a naive full-id diff over-counts.** Comparing complete impl ids reports
`OpWhereAPI`, `OpMinimumAPI`, `OpPowAPI`, `OpClipAPI`, `OpATan2API`,
`OpFloorDivideAPI`, `OpNotAPI`, `OpHypotAPI` as missing, but those *are*
implemented on `DeviceCuda` with a different generic arity (`impl<T, D>` vs
`impl<TA, TB, D>`), which changes the HTML id. The trait-name comparison above
is the corrected method.

## 3. Compile probes

A throwaway crate at `/tmp/cudaprobe` with path dependencies on `rstsr-core`
and `rstsr-cuda`, built with `CUDARC_CUDA_VERSION=12060` (no nvcc on PATH):

```toml
[dependencies]
rstsr-core = { path = "/scratch/rstsr_pack/rstsr/rstsr-core" }
rstsr-cuda = { path = "/scratch/rstsr_pack/rstsr/crates-device/rstsr-cuda" }
num = "0.4"
```

**Probe 1 — unary neg.**

```rust
let dev = DeviceCuda::new(0);
let a: Tensor<f64, _, _> = asarray((vec![1.0f64, -2.0], &dev));
let b = -&a;
```

```text
error[E0600]: cannot apply unary operator `-` to type
  `&TensorBase<Storage<DataOwned<CudaBuffer<f64>>, f64, DeviceCuda>, _>`
note: `rstsr_cuda::device::DeviceCuda` does not implement
  `OpNegAPI<f64, f64, std::vec::Vec<usize>>`
```

**Probe 2 — complex and integer `sum`.**

```rust
let z: Tensor<num::Complex<f64>, _, _> = asarray((vec![Complex::new(1.0, 2.0)], &dev));
let _ = z.sum();
let i: Tensor<i32, _, _> = asarray((vec![1i32, 2, 3], &dev));
let _ = i.sum();
```

Both fail with `E0599`: `the method 'sum' exists … but its trait bounds were
not satisfied`. `ReduceAcc` is implemented only for f32/f64
(`src/kernels/reduce_unary.rs:115,123`).

**Probe 3 — bool `sum`.**

```rust
let b: Tensor<bool, _, _> = asarray((vec![true, false, true], &dev));
let _ = b.sum();
```

Compiles (count kernel via `OpSumBoolAPI`, `src/reduce_ops.rs:530`).

## 7. What was not verified

- **No hardware run for this directory.** The 183-test green run is quoted
  from the pinned-host record at `9c7d49a`, not re-executed.
- **No benchmark run**, so no current elementwise/reduction/matmul numbers.
- **Multi-GPU** behavior is inferred from code (`memcpy_dtod_async` without
  peer access); there is one GPU on this machine and no test.
- **Arch matrix** (`./scripts/arch-matrix.sh`) was not re-run; its result is
  quoted from the PR/commit record.
- **`rstsr` facade wiring** is absent by inspection of `rstsr/Cargo.toml` and
  `rstsr/src/prelude.rs`; no build was attempted with a `cuda` feature because
  the feature does not exist.
- **`from_nested`/`pack_array`/`TensorArc`** rows in
  [COVERAGE.md](COVERAGE.md) are marked `P` because they were not exercised;
  they are not claims of breakage.
